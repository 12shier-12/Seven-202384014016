# Triply — Offline-First Trip & Packing Planner

> A pure front-end travel planner that needs no account and works offline: itineraries are organized day by day, and the packing list is generated by a rule engine from **trip length, party size, activity tags and expected temperature**.

There is no backend at all — every byte lives in the browser (IndexedDB). Open it and go; closing the tab loses nothing, and you can still tick off luggage with the Wi-Fi turned off.

**Live demo**: run `pnpm build` in this folder and host `dist/` on any static server.

---

## Why this exists

Before every trip I end up handwriting the schedule in a notes app, asking friends on WeChat whether to bring a hairdryer, and by the end the checklist is spread across three different places. Existing trip apps either require a social account or lean heavily on map and weather services, so half of the app dies offline. Packing, meanwhile, is usually something you start from scratch every time.

Triply closes that small loop: **create a trip → plan each day → get an automatic packing list → tick items off → export or print**. No account, no server, no ads; the data stays on your own machine.

## Features

Checked items are available in the current build; unchecked ones are planned.

### Trip management

- [x] Trip CRUD: name, destination, start and end dates, party size, budget, notes, cover emoji
- [x] Card list sorted by departure date, automatically labelled upcoming / ongoing / past
- [x] Trip overview: day count, activity count, total budget, packing progress bar
- [x] Empty states: create a trip or load the sample data

### Day-by-day itinerary

- [x] One column per day (Day 1, Day 2, …), each with its own activity list
- [x] Activity fields: title, start time, duration, location (plain text), type, tags, budget, notes
- [x] Reordering: move up / move down within a day, and "move to Day N" across days (drag-and-drop planned for week 2)
- [x] Time conflict detection: overlapping activities are highlighted and name the activity they clash with
- [x] Daily subtotal: number of activities and total budget

### Packing list (the differentiator)

- [x] Rule engine: matches rules by trip length + party size + activity tags + temperature range
- [x] 12 built-in rules: documents, toiletries, electronics, clothes by day count, quantities by party size, cold / hot weather, rain, hiking, beach, long trips, medicine, overseas travel
- [x] Quantity expressions such as `min(days, 7)`, `ceil(days / 3)`, `travelers * 2` — no `eval`
- [x] Enable / disable rules and override suggested quantities (custom rule editing is planned)
- [x] Manually added items with name, quantity, category, required flag and packed state
- [x] Grouped by category with a progress bar ("X / Y packed") and a remaining-required counter
- [x] Copy the whole list as plain text to send to travel companions

### Data and export

- [x] IndexedDB persistence via Dexie, with a versioned schema
- [x] Full JSON export / import (`schemaVersion` checked, confirmation before overwriting)
- [x] CSV export with a UTF-8 BOM so Excel opens it correctly
- [x] Print stylesheet (`@media print`) for a paper checklist

### Optional, if time allows

- [x] PWA: install to desktop / home screen, offline caching
- [ ] Departure reminders via the Notification API (3 days and 1 day before)
- [ ] Budget vs. actual spending chart
- [ ] Trip templates ("3-day city break", "7-day hike")

## Getting started

Requires Node.js >= 20 and npm >= 10 (the repo ships `pnpm-lock.yaml`, so pnpm installs faster).

```bash
git clone https://github.com/12shier-12/Seven-202384014016.git
cd Seven-202384014016/week4
pnpm install       # or npm install
pnpm dev           # http://localhost:5173
pnpm test          # unit tests + jsdom smoke tests
pnpm test:cov      # coverage, focused on src/core
pnpm build         # production build into dist/ (also emits manifest + service worker)
pnpm preview       # preview the production build locally
```

On first launch the app seeds sample data (a 7-day Kyoto trip, a 3-day Chengdu trip, a 2-day Hangzhou weekend), so there is something to look at without typing anything. To start over: Settings → Reset to sample data.

## Design notes

### 1. The packing list is derived, never merged

The usual approach materialises rule output into `PackingItem` rows and then offers a "Regenerate" button that has to three-way-merge rule changes against user edits. That is the classic bug farm of this product category — the edge cases never end.

Triply stores only the user's choices:

```ts
interface PackingState {
  tripId: string;
  // key = `${ruleId}:${itemName}`; records only deviations from the suggestion
  overrides: Record<string, { qty?: number; packed?: boolean; removed?: boolean }>;
  manual: PackingItem[]; // items the user added by hand
}
```

The list is recomputed by a pure function on every render:

```ts
buildPackingList({ trip, activities, rules, state }): { groups, summary, matchedRuleIds }
```

- A rule adds an item → it simply appears, no migration needed
- User edits quantity or ticks an item → written to `overrides`, survives recomputation
- User deletes an item → recorded as `removed: true` (a tombstone), not a hard delete; re-enabling the rule restores the user's edits
- Rule disabled → its items disappear, but the overrides are kept

There is no "Regenerate" button, and therefore no merge bug. The whole pipeline is unit-testable, and it makes a good story for the final presentation: **replacing state merging with stateless derivation**.

### 2. Quantity expression engine (no `eval`)

Quantities depend on trip length and party size, and hard-coded numbers make rules brittle, so each quantity is a restricted expression:

```
expr    := term (('+' | '-') term)*
term    := unary (('*' | '/') unary)*
unary   := '-' unary | primary
primary := number | ident | ident '(' args ')' | '(' expr ')'
```

- Variable whitelist: `days`, `travelers`, `minTemp`, `maxTemp`
- Function whitelist: `min`, `max`, `ceil`, `floor`, `round`, `abs`
- Implementation: tokenizer → AST → evaluator, with ASTs cached by expression string
- Rules are validated on save; invalid expressions report a character offset, e.g. `unknown variable "temp" (position 9)`
- Division by zero, negative and fractional quantities are normalised to a legal value instead of throwing

Avoiding `eval` is a practical decision: rules are user-editable, and `eval` would mean arbitrary code execution. A hand-written parser also gives readable error locations.

### 3. Time conflict detection

Convert `HH:mm` to minutes, treat each activity as `[start, start + duration)` with a 60-minute default, sort by start time and sweep an active list:

```
conflict when a.start < b.end && b.start < a.end
```

- Touching but non-overlapping (`a.end === b.start`) is not a conflict
- Activities without a start time are skipped and sorted to the end of the day
- Returns conflicting pairs rather than a boolean, so the UI can say "overlaps with Kiyomizu-dera"
- O(n log n); dozens of activities are free

### 4. Dates and day counts

Storage uses `YYYY-MM-DD` everywhere; arithmetic normalises through `Date.UTC(y, m, d)` so local time zones and daylight saving never shift a date by one day.

- Day counts are inclusive: `2026-03-01` to `2026-03-03` is 3 days
- Trip status compares against today's local date string: before start = upcoming, inside the range = ongoing, after end = past
- Never mix `new Date('2026-03-08')` (parsed as UTC) with `new Date()` (local time)

### 5. Data model

```ts
type TripId = string;

interface Trip {
  id: TripId;
  name: string;
  destination: string;
  startDate: string;            // YYYY-MM-DD
  endDate: string;              // YYYY-MM-DD
  travelers: number;
  budget?: number;
  expectedTemp?: { min: number; max: number }; // temperature input for rules; estimated from month if omitted
  coverEmoji: string;           // lightweight cover instead of image uploads
  notes?: string;
  createdAt: number;
  updatedAt: number;
}

type ActivityType = 'transport' | 'stay' | 'sight' | 'food' | 'shopping' | 'other';

interface Activity {
  id: string;
  tripId: TripId;
  dayIndex: number;             // day number, starting at 1
  title: string;
  startTime?: string;           // HH:mm
  durationMin?: number;
  location?: string;            // plain text, no map integration
  type: ActivityType;
  tags?: string[];              // hiking / beach / ski … rules match on tags
  budget?: number;
  notes?: string;
  order: number;                // position within the day
}

type Category = 'clothes' | 'toiletry' | 'electronics' | 'documents' | 'medicine' | 'other';

interface PackingItem {
  key: string;                  // `${ruleId}:${name}` for rule items, a uuid for manual items
  name: string;
  qty: number;
  category: Category;
  required: boolean;
  packed: boolean;
  source: 'rule' | 'manual';
  ruleId?: string;
}

interface PackingRule {
  id: string;
  name: string;
  enabled: boolean;
  priority?: number;
  when: {
    activityTypes?: ActivityType[];
    tags?: string[];
    tempRange?: [number, number];  // fires when the ranges intersect
    minDays?: number;
    minTravelers?: number;
  };
  then: Array<{ name: string; qtyExpr: string; category: Category; required?: boolean }>;
}
```

Two design rules:

1. **Rules and items are separate.** Rules only suggest; the user's actual state lives in `PackingState`, and the two never overwrite each other.
2. **Same-name items are de-duplicated.** When two rules produce the same item in the same category, the quantity takes `max` rather than the sum, so you never end up packing "12 pairs of socks".

## Data and privacy

- Storage: IndexedDB (Dexie); tables `trips`, `activities`, `packing`, `rules`, `meta`
- Migrations: `db.version(1).stores({...})` declares tables and indexes; later versions add `db.version(2).upgrade(...)`. The `meta` table holds the seed flag
- Export: a `{ schemaVersion, exportedAt, data: {...} }` envelope, ready for future upgrades
- Import: structure and version are validated, the user confirms, and then the dataset is fully replaced — never silently
- No accounts, no analytics, no third-party requests. The only optional network feature is weather; without an API key it falls back to manual input and nothing else changes

## Deployment

Pushing to `main` runs the tests, builds, and publishes to GitHub Pages via `.github/workflows/deploy.yml`.

Key configuration:

```ts
// vite.config.ts
export default defineConfig({
  base: './', // relative asset paths: no 404s on any repo sub-path
  plugins: [react()],
});
```

- `HashRouter` avoids 404s when a child route is refreshed on Pages, so no `404.html` fallback is needed
- The build output goes to `dist/` and is uploaded by `upload-pages-artifact`
- PWA is generated at build time (`vite-plugin-pwa`, `registerType: 'autoUpdate'`): the service worker precaches the app shell, so the app opens offline and does not get stuck on a stale cache
- After the first deploy, open the link on a phone and use "Add to Home Screen", then turn on airplane mode and reopen the app

### Install and offline behaviour

`pnpm build` emits `manifest.webmanifest`, `sw.js` and the Workbox runtime next to the normal assets.
The manifest is installable (192 px, 512 px and a maskable icon), and the precache includes the HTML,
JS, CSS and icons, so the whole planner works with no network after the first visit. Data still lives
in IndexedDB, so an offline session keeps writing to the same local database.

## Non-goals

Written down to keep the scope from creeping:

- No map SDK or route planning (external services make live demos fragile)
- No real weather API as a requirement (optional only; manual input by default)
- No sign-up, collaboration, or share-permission model
- No payments, orders, comments, or image uploads
- No backend sync; data stays on one device and moves via JSON import / export

## Known limitations

- Single-device data: switching devices means exporting and importing JSON
- Locations are plain text; there is no map lookup or distance estimate
- Packing suggestions come from built-in rules and do not cover destination-specific documents or customs requirements
- IndexedDB can be disabled in private browsing, in which case data cannot be saved (no read-only fallback yet)
- UI copy is currently Simplified Chinese; internationalisation is not implemented yet
